## 0. 一句话结论

做一个**离线、双击即开、不需要起服务**的单页工具：以「**Buff 来源矩阵**」为骨架，把
「我这条 BD 需要哪些 buff → 每个 buff 有哪些获取途径 → 我实际拥有哪些 → 缺的怎么补最便宜」
这四件事串成一条可计算的链路，再向外扩展到「词条搭配器」。

不做第二个 DPS 计算器（社区已有），做**决策层**：算"该怎么补、补哪个划算"。

## 1. 你要解决的三个问题，拆成三块可计算的模型

| 你的原话 | 拆解 | 本工具的对应模块 |
|---|---|---|
| 自身一些词条搭配 | 槽位 × 前缀/后缀 × 侵蚀/高塔/调香等附加词缀，受"同组互斥 / 条数上限 / 底材限制"约束 | **词条搭配器**（M5） |
| buff 获取、这些 buff 从哪些地方获得 | buff 是"实体"，来源是"边"，构成一张二分图；一个 buff 常有 5~10 条获取边 | **来源矩阵**（M2，MVP 核心） |
| 自己是否拥有这些 buff | 由"已选配置"推导 + 玩家实测勾选，两者交叉校验 | **覆盖判定 / 缺口看板**（M3） |
| 性价比如何 | 每条来源边带"代价向量"，每个 buff 带"需求强度"，相除排序 | **性价比评分**（M4） |

关键认知：**"是否拥有"不是查表，是求解**。同一句「至少拥有 6 层任意祝福」，在
英雄 A + 天赋 B + 装备 C 的组合下成立，换一件装备就崩。所以它必须由配置推导，而不是手填。

## 2. 形态选型：网页 vs 可执行文件（直接回答你的顾虑）

你的顾虑是「网页是不是每次都要重新启动，比较麻烦」。**这个顾虑只对"需要跑服务器的网页"成立**，
对本项目不成立。

### 2.1 结论：静态单页 + `file://` 直开 + 应用模式快捷方式

| 方案 | 每次启动代价 | 改动迭代 | 数据更新 | 当前环境可行性 |
|---|---|---|---|---|
| **静态页 + 双击（选定）** | 0（双击图标 ≈ 0.3s 打开浏览器） | 改文件 → 刷新 | 替换 `data/*.js` | ✅ 无需 shell |
| 静态页 + 本地服务（`vite preview`） | 要起进程、守端口，忘了关就残留 | 中 | 中 | ❌ 当前 shell 挂 |
| Electron / Tauri 打包 exe | 双击 ≈ 1s（比浏览器还慢） | 每次改 UI 要重打包（分钟级） | 要重打包 | ❌ 需要工具链 |
| Excel 表格 | 快 | 差（无计算/无联动） | 手动 | ✅ 但表达力不够 |

**为什么不做 exe**：Tauri/Electron 的唯一优势是"像个应用"，但它把迭代成本从"刷新"抬高到"重新打包"，
而本项目的特点恰恰是**数据与规则会频繁改**（赛季更新、你的理解迭代）。而"像个应用"这件事，
用一个 `.cmd` 调用浏览器 `--app` 模式就能拿到：

```
启动规划器.cmd
  → msedge --app="file:///D:/Code_reporsty/Torchlight_BuildsPlanner/index.html"
  → 无地址栏、无标签页、独立窗口、可固定到任务栏
```

将来若真想要 exe：**同一套前端**直接塞进 Tauri，迁移成本≈0（因为它本来就是纯静态）。
所以现在选静态页不影响任何后路。

### 2.2 为此必须遵守的三条工程约束

1. **不用 ES Module、不用 `fetch()` 读本地 JSON**——`file://` 下会被 CORS 拦死。
   数据用 `<script src="data/xxx.js">` 注入 `window.TLI_*`，普通脚本天然可用。
2. **不引 CDN**——无网络时也要能开。所有 CSS/JS 自带。
3. **存储降级链**：`localStorage`（`file://` 下个别浏览器策略会拒）→ 失败时自动切「导出/导入 JSON」
   模式，并在界面提示。绝不因为存不了档就崩。

### 2.3 数据更新怎么不重启

- 常规：`node tools/build-data.mjs` 重新生成 `data/*.js` → 页面刷新（F5）即可。
- 应急：页面里直接**拖入 JSON** 覆盖当前数据集（不需要 shell），用于临时改一条词条。

└───────────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌──────────────────────── 引擎层（纯函数，可在 Node 里单测）─────────────────────────────┐
│  resolveBuild(cfg) → { granted:[], caps:{}, unmet:[], warnings:[] }                    │
│  gapSolve(requirements, pool) → [{ plan, costScore, coverage }]                        │

└───────────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼

**为什么引擎独立**：判定逻辑（层数、互斥、缺口求解）是整个项目里唯一"会反复改且容易错"的部分，
把它写成纯函数、能用 `node --test` 跑用例，比在 UI 里 `if` 满天飞可靠得多。

### 4.2 抓取流程（分两阶段，避免"盲写解析器"）

**阶段 A：只抓不改** — `tools/fetch-tlidb.mjs`
- 按 `tools/pages.json` 清单抓取，并发 3、间隔 400ms、失败重试 3 次（指数退避）
- 落盘 `data/raw/<slug>.html`，已存在则跳过（断点续抓）
- 生成 `data/raw/manifest.json`（URL、抓取时间、字节数、sha256）——**用来判断赛季是否变更**

**阶段 B：先看结构，再写解析** — `tools/inspect-html.mjs`
- 输出标签直方图、候选卡片容器的 class 分布、前若干样本片段
- 我据此写 `tools/parse-*.mjs` 精确解析，而不是猜选择器

**阶段 C：规范化 + 打包** — `tools/build-data.mjs`
- 合并 raw 解析结果 + `data/patches/`（人工修正）+ `data/buffs.dict.json`（buff 词典）
- 输出 `data/tli.js`（体积大，分片：`tli-affix.js` / `tli-skill.js` / `tli-gear.js`）
- 写 `data/meta.js`：赛季号、生成时间、各表条数、数据完整度标记

### 4.4 关键难点：`modsText` → 结构化

「至少拥有 6 层坚韧祝福时，额外 +38% 伤害」这种条件句，必须能机器判定，否则"我是否拥有"永远是人工。

两级策略（不要一步到位）：

1. **M2 阶段：关键词 + 条件抽取**（够用）
   - buff 词典给出别名表（`坚韧祝福|坚韧|Tenacity`），扫全库文本反查 → 得到 buff↔来源的**反向索引**
   - 条件句用少量正则模板抽取：`至少拥有 (\d+) 层(.+?)(时|，)` / `每有 ?(\d+) ?层` / `上限 \+?(\d+)`
   - 抽不出来的一律标 `unparsed`，UI 里**原样展示 + 灰色标记**，绝不猜（宁可漏，不可错）
2. **M5 阶段：模板解析器**（参考 aclinia 的 `mod-parser/templates.ts` 思路）
   - 把「文本模板 → 结构化 mod」做成表，配 golden test，逐条补

## 5. Buff 领域模型（本项目最核心的设计）

### 5.1 buff 分类（第一版）

| 家族 | 例子 | 为什么单列 |
|---|---|---|
| **祝福 blessing** | 聚能祝福 / 坚韧祝福 / 灵动祝福 | 有**层数上限**机制，是最典型的"配置决定有无"的 buff |
| **光环 aura** | 狂猛、武器增幅、能量壁垒、元素抵抗、灵敏、暴虐…（cn 页 48 条） | 占**技能位**，有「同名只生效一个、精密 > 等级 > 效果加成」的裁决规则 |
| **增益 buff** | 各类"最近…时"、"获得…"的临时正面效果 | 触发条件多，性价比差异最大 |
| **资源/充能 resource** | 战意、充能类、灵药/药剂层数 | 常与"上限/回复速度"联动 |
| **减益 debuff** | 敌人身上的点燃/冰结/感电/中毒/凋零/创伤… | 很多 buff 的要求是"对带 X 的敌人"，必须能查"我怎么稳定施加 X" |
| **未知/待补 unknown** | 抽不出结构的条目 | 显式暴露，避免工具假装完整 |

### 5.2 「拥有」的三态判定（解决你的核心问题）

对每个 buff，在同一套配置下算出四个量：

```
granted   : 配置直接给出的层数/效果（求和）
cap       : 层数上限（基础上限 + 所有 "+上限" 词条）
actual    : min(granted, cap)                  ← 理论实际层数
measured  : 玩家实测填的值（可空）
```

于是状态天然是三态 + 一个矛盾态：

| 状态 | 判定 | UI |
|---|---|---|
| **已拥有** | `actual ≥ 1` 且（无条件未满足） | 🟢 |
| **条件性拥有** | 有 granted，但 `stacks < 需求层数` 或前置未满足 | 🟡 显示"差几层/缺什么前置" |
| **不具备** | `granted = 0` | ⚪ |
| **理论有·实测无** | `actual ≥ 1` 但 `measured = 0` 或 `measured < actual` | 🔴 高优先级告警：说明某条链没真正跑起来（触发顺序、CD、范围、被覆盖规则） |

最后这条是**最有价值的功能**：它把"攻略说有、我打起来没有"这类玄学问题变成一条可追的差异。
（典型成因：光环被同名覆盖、祝福被"上限"词缀压掉、状态在进图前未叠、触发 CD 与攻速不匹配）

### 5.3 需求（requirement）模型

buff 的"需求"来自两个方面，都要能表达：

1. **词条要求**：如「至少拥有 6 层任何祝福」→ `req(buff=blessing.any, stacks≥6)`
2. **玩家目标**：我自己定的目标，比如"我要稳吃 10 层坚韧祝福的转化效果" → 手动建 requirement

requirement 支持：`stacks≥N`、`cap≥N`、`has(buff)`、`conditional(expr)`、`atLeastOne(buffSet)`。
缺口看板 = 满足不了的 requirement 列表，按"影响面"排序（被多少条已选词条依赖）。

## 6. 来源矩阵（MVP 的信息结构）

一个 buff 的详情页，右侧是**来源表**，每行是一条获取途径：

| 列 | 内容 |
|---|---|
| 类型 | 传奇装备 / 词缀 / 天赋 / 核心天赋 / 英雄特性 / 光环技能 / 辅助技能 / 契灵 / 神格石板 / 追随者 / 打造 |
| 来源 | 名称（可点开原文） |
| 提供 | 定量描述：`+1 层上限` / `每 2 秒 +1 层` / `+38% 伤害（条件：≥6 层）` |
| 代价 | 代价向量渲染成小徽标：`词条位×1` `技能位×1` `天赋点×3` `🔥 12` `操作负担:中` |
| 前置 | 英雄=艾瑞卡 / 需 6 层 / 需装备双手剑 … |
| 我选了 | 勾选（= 这条已经在你 build 里） |
| 链接 | tlidb 原始页（离线可跳转） |

排序：默认按**性价比**（M4 才有，M2 先按"可行性"：无前置 > 有前置 > 需换英雄）。
筛选：只看"我没选但能补"的、"不需要换英雄"的、"低于 X 火"的。

交互上必须支持**反向视角**：从"我拥有的装备/天赋/技能"出发，看"这些我白拿了哪些 buff"
（很多时候答案是：你已经能吃到，只是不知道）。

## 7. 性价比模型

### 7.1 代价向量（cost vector）

不给单一价格，给向量，因为"换英雄"和"花 12 火"不可通约：

```jsonc
"cost": {
  "currency": { "amount": 12, "unit": "火" },        // 交易行/打造，手填，可缺省
  "gearSlots": 1,                                    // 占一个词条位
  "skillSlots": 0,                                   // 占一个技能位
  "passiveSlots": 1,                                 // 占被动技能位
  "talentPoints": 3,
  "heroLock": null,                                  // 或 "艾瑞卡/寻仇之刺"
  "load": "中"                                       // 操作/维持负担：低/中/高
}
```

加权成 `costScore = Σ wᵢ · normalize(costᵢ)`，权重**用户可在设置里改**（因为你的"贵"和别人的"贵"不一样：
有人缺火，有人缺词条位）。

### 7.2 收益（benefit）

不用"DPS 提升多少"（那是 DPS 计算器的活，且依赖大量未解析公式），改用**需求覆盖度**：

```
benefit = Σ_{requirement}  依赖度(req) × 边际贡献(source→req)
```

- `依赖度`：该 requirement 被多少条**你已选**词条依赖（来自 4.3 的反向索引）→ 天然反映"这条 buff 对你有多重要"
- `边际贡献`：这条来源把 `actual` 从多少推到多少（饱和即 0，避免"再加一层上限"的虚假收益）

### 7.3 输出

1. **排序表**：`benefit / costScore` 降序 —— "最划算的补法"
2. **缺口求解**：对每个未满足 requirement，枚举 1~3 条来源的组合（在"你拥有的资产 + 可买"池里），
   输出前 3 个最省方案，标明"还差几层/几火"
3. **反事实**：勾掉某条来源后重算 —— "如果我把这件传奇换成别的，会丢哪些 buff"（这个功能比排序表更常用）

### 7.4 明确不做的

- 不做完整 DPS 计算（公式巨大、维护成本高、且已有成熟工具）
- 不做自动市场比价（无公开 API；改为手动维护一张 `prices.json`，10 条就够影响排序）
- 不给"最优解"这种伪精确结论，只给"在你当前约束下的相对排序"

## 8. 词条搭配器（M5，等矩阵稳定后）

结构：`槽位 → 底材 → 前缀池/后缀池 → （侵蚀/高塔/调香/缝合 附加）`。

校验规则（按优先级）：
1. **底材限制**：该词缀是否允许出现在此底材（tlidb 已按槽位分表，天然满足）
2. **互斥组**：同一 `group` 只能出现一条（如多条"附加伤害"类）
3. **条数上限**：前缀 ≤ N、后缀 ≤ N（随打造方式变化）
4. **T 级与 ilvl**：所选 T 级要求的最低物等是否达到
5. **数值区间**：给定 roll 是否落在该 T 级区间内（超出即标红）

输出：组合卡片 + 冲突红标 + **与 buff 需求的联动**（这套词条能提供哪些 buff 的层数/上限）。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 当前 `pwsh` 启动即崩（`0xC0000142`，DLL 初始化失败） | 跑不了 node/npm，抓取与构建全停 | M0 全部用纯文件实现；抓取脚本先写好；建议重启终端/DSH 后再跑 M1 |
| tlidb DOM 结构变动 | 解析器失效 | 解析器与抓取分离；manifest 存 sha256；失效时只重写解析层 |
| 赛季改动导致词条重写 | 数据错位 | `meta.season` 强校验；跨赛季只做"新增/删除/改文本"三分类复核 |
| 条件句解析错误 | "拥有"判定不可信 | 解析失败一律 `unparsed` + 原样展示；关键结论要求人工点一次"确认" |
| 官方流派码格式未知 | 无法一键导入已有角色 | 先支持手工勾选 + localStorage 存档；流派码作为 M5 探索项（社区已有 base64/fflate 实现可参考） |
| 价格数据缺失 | 性价比失真 | 价格表留空时自动降级为"非货币代价排序"，并显式提示"未含火价" |
| 数据版权 | — | 仅自用；仓库提交的是结构化派生数据 + 来源链接，不分发原始页面 |

## 11. 需要你拍板 / 后续补充的点

1. **价格来源**：性价比里的"火"你打算怎么维护？我建议先手填 10~20 条（你常买的几类）。

5. **数据粒度**：词条要不要到"T1~T7 + 数值区间"粒度？（做搭配器必须要；只做矩阵可以先粗）

## 附录 A：已核实的机制原文（用于校准模型）

**光环效果**（[tlidb /cn/Aura](https://tlidb.com/cn/Aura)）
> 正面效果数值 = 基础数值 × (1+所有非额外百分比加成) × (1+额外百分比加成1) × (1+额外百分比加成2)…
> 多个同名光环技能将要对同一单位生效时，只有一个光环能够生效。
> 精密级别的光环技能优先生效，之后按照 等级 > 效果加成数值 的优先级，值较大的光环技能生效。

**祝福体系**（[tlidb /cn/Blessing](https://tlidb.com/cn/Blessing)）
> 祝福包括聚能祝福、坚韧祝福、灵动祝福。
> 装备可提供"（-1~1）X祝福层数上限"这类负向/正向上限词条；传奇可给"至少拥有 6 层任意祝福时 +15~20% 双倍伤害"。
> 猫3 示例：「命悬一线」把凌厉效果绑在灵动祝福层数上（每层 +40%，上限 10 层）——这就是"上限/闸门"类联动的典型。

→ 这三条直接决定了引擎里必须有：`cap 与 granted 分离`、`同名裁决`、`上限可被负向词条压掉`。
